# The Campus on Render free + Turso free (DEV ONLY, 2026-11-19)

> **Name (2026-11-19):** the product is now **The Campus** (user-facing branding only). Technical identifiers are unchanged on purpose: Turso database `the-quad`, GitHub repo `Kazi477/the-quad`, Render service `the-quad-free` (URL `https://the-quad-free.onrender.com`). The object-storage bucket suggestion is `the-campus-media` because that bucket does not exist yet.

No payment, no card, friends can open a live link, accounts and posts
live on a server and survive restarts. This is the route Mitchell
chose (option 3) after PythonAnywhere's email-verification gate kept
blocking the dashboard.

## Why this combination

| Piece | Free tier | Catch |
|---|---|---|
| Render web service, `plan: free` | 750 instance-hours/month, 512 MB RAM, no card, no expiry on the compute itself | Sleeps after 15 min idle (30–60 s cold start); **ephemeral disk** — anything written to local disk is wiped on restart |
| Turso, free tier | 5 GB storage, 100 databases, 500M row reads / 10M writes / 3 GB syncs per month, no card, GitHub sign-up, does not expire | Writes are the tightest limit (~3.8/sec sustained); point-in-time restore only 1 day |

Render free alone cannot hold The Campus's data: its SQLite file would
be deleted on the first sleep/restart. Turso holds the durable copy;
the app runs as a libSQL **embedded replica** (local file + cloud
sync), so a wiped Render disk just re-syncs from Turso on startup.

## What changed in the code

* **New: `db_backend.py`** (310 lines) — the only new module. When
  `TURSO_DATABASE_URL` + `TURSO_AUTH_TOKEN` are set, `connect()`
  opens the database through libSQL's embedded replica, wrapped so
  it looks like `sqlite3` to the app (name-addressable rows,
  `with` blocks, `executescript`, `lastrowid`, errors translated to
  `sqlite3.Error`/`IntegrityError`). Without those env vars the app
  never imports libSQL and runs exactly as before, stdlib-only.
* **`the_network_production.py` 2406 → 2449 lines** — two surgical
  changes only: `connect()` dispatches to `db_backend` in Turso
  mode, and `backup_database()` syncs the replica then copies the
  local file with the sqlite3 backup API (libSQL has no `.backup()`).
  No routes, auth, or features changed.
* **New: `render-free.yaml`** — the deploy file. `plan: free`, no
  disk, `healthCheckPath: /healthz`, `DATA_DIR=/tmp/quad-data`
  (ephemeral on purpose), `TURSO_DATABASE_URL` / `TURSO_AUTH_TOKEN`
  as `sync: false` secrets. The paid `render.yaml` is untouched
  (backup kept as `render.yaml.bak-paid`); the pre-change code is
  kept as `the_network_production.py.bak-renderfree`.
* **New: `requirements.txt`** — `libsql-experimental==0.0.55`.
* **`Dockerfile`** — installs `requirements.txt` and copies
  `db_backend.py` into the image. Nothing else changed.
* **New: `render_free_test.py`** — 30 checks (see Tests below).

## Limits — read before approving

* **Real Turso cloud sync is UNTESTED in dev.** No Turso account
  was created here (that needs Mitchell's GitHub sign-up). The
  wrapper and the whole app are tested end-to-end against a local
  libSQL file (same driver, same code path). The first real deploy
  is the first live sync test. If the sync URL is unreachable at
  startup the app fails loudly instead of silently running
  local-only (tested: an invalid URL never serves `/healthz`).
* **Uploads are still ephemeral.** Photos/videos go to
  `DATA_DIR/network_uploads/` on Render's disk and are **lost when
  the instance sleeps/restarts**. Post text, accounts, friends,
  messages and everything in the database survives (Turso); an
  uploaded photo attached to a post will break after a restart.
  Fixing that properly needs object storage (e.g. Cloudflare R2
  free tier) — a follow-up, not in this build. Until then, tell
  users photos may disappear, or disable uploads.
* **Uploads — FIXED in Update 11 (object storage).** Photos and
  videos now go to an S3-compatible object store (Cloudflare R2
  free recommended, Tigris as the no-card fallback) when the
  `OBJECT_STORAGE_*` env vars are set in `render-free.yaml`
  (endpoint, bucket, access key, secret key — all `sync: false`
  secrets, pasted in the Render dashboard). The bucket stays
  private and the app proxies bytes through `/media/` after its
  own permission check, so private photos stay private. R2 free:
  10 GB, 1M Class A / 10M Class B ops/month, $0 egress. **Caveat:
  R2 signup may ask for a payment method on file — if it does,
  do NOT add a card; use Tigris instead (5 GB, no card).** See
  "Object storage" below and `object_storage.py`. Without the env
  vars the app still falls back to local disk (and photos are
  still lost on restart).
* **Sleep / cold start.** Free instances spin down after 15 min
  idle. The first visitor after that waits 30–60 s. Render's free
  plan also has 750 instance-hours/month per workspace — one
  service fits comfortably.
* **Dual backend / failover (Update 8) does NOT apply here.**
  Render free is one instance only, no second backend, no nginx
  front door. If the instance is down, the site is down until
  Render wakes it. The Turso replica only protects the *data*.
* **Video uploads will be rejected** — the Docker image has
  ffmpeg, but `ffprobe` duration checks run server-side and the
  free instance is small; image uploads (≤ 8 MB) work.
* **Emailed password-reset codes will not send** until SMTP is
  configured (no credentials exist; Render free also blocks
  outbound ports 25/465/587). Recovery codes (Update 7) are the
  working path.
* **Turso write limit.** 10M row writes/month sounds large, but
  the app writes a lot per page view (page-view logging is
  throttled to 20/min/client; sessions/last_seen update on
  requests). For a small friends site this is fine; if it ever
  gets busy, the write counter is the first thing to watch.
* **APP_SECRET must stay stable.** It is generated once by Render
  (`generateValue: true`). If it is ever regenerated, every
  signed-in user is logged out and reset links break.

## Object storage for photos (Update 11)

Render free has no persistent disk, so photos written to local
disk were lost on every sleep/restart even though the database
survived in Turso. New uploads now go to an S3-compatible object
store instead (see `object_storage.py`, stdlib only — no boto3).

**How it works:** when `OBJECT_STORAGE_ENDPOINT` /
`OBJECT_STORAGE_BUCKET` / `OBJECT_STORAGE_ACCESS_KEY` /
`OBJECT_STORAGE_SECRET_KEY` are set, `save_upload()` PUTs the
file to the bucket (SigV4-signed, path-style) and records
`storage='object'` on the `uploads` row. `/media/<key>` fetches
the bytes server-side and serves them **after the same
permission check as before** — the bucket is private, there is
no public URL, no `r2.dev`, no CORS, no CSP change. Old local
files keep `storage='local'` and keep serving from disk; there
is no automatic migration of old photos (a follow-up script
could copy them up — not built yet). If the bucket is down, an
upload fails with a plain error and nothing is created; it
never silently falls back to local disk.

**Deploy steps (in addition to the Turso steps above):**

1. **R2 (recommended on limits):** Cloudflare dashboard → R2 →
   Create bucket (e.g. `the-campus-media`, **do NOT enable public
   access / r2.dev** — the bucket must stay private) → Manage R2
   API Tokens → Create API Token (Object Read & Write, this
   bucket only). Note the Account ID (dashboard → R2 → Overview,
   S3 API box) and the token's Access Key ID + Secret Access Key.
   Endpoint is `https://<account-id>.r2.cloudflarestorage.com`,
   region `auto`. **If signup asks for a payment method, stop
   and do NOT add a card** — use Tigris instead (below).
2. **Tigris (no-card fallback):** sign up at tigrisdata.com
   (no card), create a bucket, create an access key. Endpoint
   is `https://fly.storage.tigris.dev`. Free tier: 5 GB, zero
   egress, 10K Class A / 100K Class B ops per month — far fewer
   reads than R2, fine for a small friends site, watch the read
   counter if the site gets busy.
3. **Render:** in the service's Environment settings, set the
   four `OBJECT_STORAGE_*` vars (plus region `auto` for R2).
   Never put keys in `render-free.yaml` — they are `sync: false`
   there so Render prompts for them. Redeploy; the startup log
   says `Object storage: enabled (<endpoint>/<bucket>)`.
4. **Verify:** upload a photo post, restart the service (or
   wait for it to sleep), and check the photo still loads.
   Uploads made before this change stay local and will still
   break on restart unless migrated.

**Limits:** real-bucket sync is UNTESTED in dev (no account or
bucket was created; tests run against a local fake S3 server).
Every `/media/` view is one Class B read from the bucket (plus
one Class A write per upload), so the read counter is the thing
to watch. If the bucket is down, uploads fail and existing
photos 404 until it recovers — posts themselves still render.
Orphaned objects (e.g. after a restore window expires) are not
cleaned up automatically yet. Video uploads still need ffprobe
(present in the Docker image) and the 30-second / 25 MB limits
are unchanged; images ≤ 8 MB unchanged.
